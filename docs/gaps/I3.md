# I3. Auto-update

## Verdict

**Verified for Philium, not a blanket claim about HAL.** Philium's bundle
configuration has no updater endpoint, public key or updater-artifact setting
(`src-tauri/tauri.conf.json:20-27`), its dependency list has no updater plugin
(`src-tauri/Cargo.toml:9-39`), and startup constructs the Tauri builder directly
(`src-tauri/src/main.rs:338-341`). The requested prompt, authentication and
failed-start rollback remain work, not an existing feature
(`docs/GAPS.md:194-199`).

HAL does have a standalone CLI updater, but it is invoked only for unmanaged,
interactive chat (`../hal/src/main.rs:790-795`), with debug/opt-out guards
(`../hal/src/update_cli.rs:171-177`). Philium instead launches the bundled
`hal-desktop-server` (`src-tauri/src/hal.rs:59-70,108-120`), so that partial
implementation does not close I3.

## Current state

- Packaging already includes the HAL sidecar and declares macOS, Windows and
  Linux bundle formats (`src-tauri/tauri.conf.json:20-25`). Update the app and
  matching sidecar together, rather than independently replacing HAL.
- macOS signing is ad hoc (`src-tauri/tauri.conf.json:25`). Release automation
  and trusted OS signing are the explicit I1/I2 prerequisites
  (`docs/GAPS.md:182-199`).
- The frontend capability grants only core permissions
  (`src-tauri/capabilities/default.json:1-5`). Settings provides an existing
  settings RPC and page integration point (`src/screens/settings.jsx:593-623,681`).
- Agent state distinguishes running, waiting and idle, and late events cannot
  revive terminal states (`src-tauri/src/agents.rs:1065-1075`). Live runtimes
  hold HAL processes (`src-tauri/src/agents.rs:50-69`), and stopping one aborts
  its pump and HAL process (`src-tauri/src/agents.rs:1418-1426`). An idle label
  is therefore not permission to silently replace a live agent's process.
- Normal app exit has explicit shutdown coordination, including a documented
  main-thread deadlock constraint (`src-tauri/src/main.rs:490-508`). Reuse this
  lifecycle rather than adding a competing updater shutdown path.
- HAL's existing updater fetches a standalone Unix CLI release from its own
  endpoints (`../hal/src/update_cli.rs:1-10`); it is not a Philium release feed.

## Where the fix lives

**Philium-only**, plus Philium release hosting/CI. Add an updater backend module,
startup registration and health handshake in `src-tauri/src/main.rs`, and a
Settings/status surface in `src/screens/settings.jsx`. Extend the dependency,
capability and bundle files above. HAL requires no new interface: package its
existing sidecar with the matching app (`src-tauri/tauri.conf.json:24`).

## Proposed design

1. Resolve the latest compatible Tauri updater package at implementation time.
   Keep check/download/install decisions in Rust, expose narrow RPCs and events,
   and leave arbitrary artifact URLs and downgrade overrides out of webview RPCs.
   Use an HTTPS release feed generated from actual release artifacts, not a
   hardcoded latest release or model/version string. Follow `AGENTS.md:5-7`.
2. Generate updater artifacts in I1 CI and sign them with a dedicated update key.
   The Tauri contract authenticates artifacts with a configured public key and
   signatures, not merely a field called a signed manifest. To meet I3's literal
   signed-manifest requirement, additionally authenticate feed metadata and bind
   target, release identity and artifact digest before selecting a download.
   Keep private keys in CI only, with a rotation/recovery plan. Tauri reference:
   `https://v2.tauri.app/plugin/updater/` (Signing updates / Server Support).
3. Check unobtrusively and on explicit request. Show a non-modal update indicator
   and an explicit later/install-when-safe choice. Block installation while any
   agent is running or waiting for permission. Do not silently terminate idle
   live agents either. At confirmed installation, atomically gate new work,
   recheck all activity, drain owned processes via normal shutdown, then install.
   Include desk activity, queued work and scheduled resumes in the gate rather
   than trusting a snapshot of the agent list.
4. Treat failed-start rollback as a separate recovery mechanism, not an assumed
   updater-plugin guarantee. Preserve the last verified app plus matching sidecar,
   persist a pending-update marker, and have a platform-specific external recovery
   launcher watch for a bounded startup health acknowledgement. On crash/timeout,
   restore the known-good pair, quarantine the failed release and explain recovery.
   The acknowledgement must cover database readiness, IPC/UI readiness and HAL
   sidecar health. Repeated recovery attempts must be bounded.
5. Require backward-compatible data migrations or a tested, transactional restore
   strategy before committing an update. Do not roll application data backwards
   over newer user writes. Fail closed if retention, disk space or installer
   privileges cannot support recovery. Preserve normal signature checks during
   rollback and restrict it to the locally recorded known-good release.

## Acceptance checks

These are proposed implementation checks, not executed acceptance results.

- On real macOS and Windows clients, and Linux AppImage if supported for updates,
  install release A, run a real agent, publish authenticated release B, and check
  for updates. The conversation/tools keep progressing and no modal steals focus.
  Wait on a real permission request and verify installation stays blocked.
- Choose Later and restart the app: no surprise installation. Choose install when
  safe, race a second agent/queued dispatch against it, and prove either new work
  wins and installation defers, or installation owns the gate and new work waits.
- After consenting with no active work, install B, verify app and HAL identities,
  open the existing conversation, run a fresh query and a second query, then
  reconnect/relaunch without losing workspace settings or history.
- Feed tampered metadata, wrong-target artifacts, invalid signatures, stale
  replayed releases, offline responses and interrupted downloads. No unverified
  code executes, current agents survive, and retry remains available.
- Inject a pre-UI startup crash and a never-healthy startup after installation.
  Prove the external recovery path restores A and its HAL, preserves user data,
  reports the failure and does not retry B indefinitely. Repeat with a migration
  failure, low disk space and interrupted installer/recovery.
- Unit/integration tests cover the activity gate, persisted update state, feed
  authentication, release quarantine and recovery handshake. Run Rust regression
  tests including `pins::tests::no_stale_pins`, plus frontend build/tests and
  signed release-pipeline checks. This grounding task ran no builds or app tests,
  as required by `docs/gaps/README.md:15-17`.

## Dependencies and risks

- I1 publishes artifacts/feed, I2 supplies trusted OS packages; updater signing
  remains a separate key and trust boundary (`docs/GAPS.md:182-199`).
- I8's recorded package/config version mismatch affects release identity and
  comparison, so establish one build-derived release version first
  (`package.json:3`, `src-tauri/Cargo.toml:3`, `src-tauri/tauri.conf.json:4`).
- Recovery needs explicit platform coverage: the current bundle list includes
  DMG/app, MSI, AppImage and deb (`src-tauri/tauri.conf.json:22`). Decide and label
  unsupported update channels rather than assuming every installer can self-update.
- Key loss, feed compromise, forced downgrade, unsigned metadata and incompatible
  database changes are design risks. Do not weaken signature or version policy
  to implement recovery. Unavoidable security pins belong in `pins.rs`, with
  written maintenance rationale (`AGENTS.md:5-7`).

## Size

**L.** Plugin wiring is only one slice. Safe activity coordination, authenticated
release publication and externally supervised, cross-platform failed-start
recovery make this larger than a Settings button (`docs/GAPS.md:194-199`).
