# A3: User-configurable tool hooks

## Verdict

**Verified for the requested user feature.** HAL's configuration exposes a private
Exo authorization adapter, not user lifecycle commands (`HAL src/config.rs:29-33`).
Its hook schema accepts only protocol, profile path and profile digest, and its
executable is fixed to Exo's native policy adapter (`HAL src/security/exo_hook.rs:14-20,67-75`).
The audit's description of that adapter as merely sandbox-level is incomplete:
it already participates in before-tool decisions, including MCP, shell and file
candidates (`HAL src/agent/runtime.rs:2840-2892`), and model input/output decisions
(`HAL src/agent/runtime/exo_io.rs:260-267,382-404`). It is not an extensible user
command runner or an after-tool/context injection facility (reply fields:
`HAL src/security/exo_hook.rs:21-39`). Here and below, `HAL` means the read-only
checkout at `~/Developer/hal`.

## Current state

- HAL's config has permissions, private Exo controls, prompt commands, MCP and
  experimental evaluators, but no user lifecycle-hook collection
  (`HAL src/config.rs:17-73`). Philium currently generates only server,
  default-model and model configuration in its shared setup builder
  (`src-tauri/src/providers.rs:357-360`).
- Exo's hook runs a bounded subprocess with structured input, a 20-second
  deadline, bounded output and validated allow/deny/approval receipts
  (`HAL src/security/exo_hook.rs:60-139`). Failure prevents tool execution and
  fresh policy decisions are composed with other mandatory verdicts
  (`HAL src/agent/runtime.rs:2875-2895`). These are useful implementation
  patterns, not permission to replace that security authority with user code.
- The common dispatcher executes tools then records results and emits
  `ToolFinished`; this is the natural before/after seam, not an event-only
  Philium listener that would be too late to block execution
  (`HAL src/agent/runtime.rs:3024-3059,3086-3111`).
- There are lifecycle seams at session creation and turn completion
  (`HAL src/session/mod.rs:668,780`; `HAL src/agent/runtime.rs:1600-1638`).
- Philium writes generated HAL config containing a gateway token, strips known
  credential variables, supplies a desktop token and optionally hides login
  directories (`src-tauri/src/hal.rs:103-127`). Therefore simply inheriting HAL's
  environment or readable config is not a safe hook credential boundary.
- Agent launches already choose sandbox wrapping, while HAL shell subprocesses
  apply `sandbox_command` and process groups (`src-tauri/src/agents.rs:789-795`;
  `HAL src/tools/shell.rs:255-273`). Reuse these isolation concepts rather than
  copying Exo's unrestricted `Command::new` path into user hooks.

## Where the fix lives

**Both.** HAL owns synchronous lifecycle dispatch, hook subprocess supervision
and bounded context insertion at the tool/turn seams above. Add an upstream
user-hook config/runner module alongside `HAL src/config.rs` and wire
`HAL src/agent/runtime.rs` plus `HAL src/session/mod.rs`. Do not repurpose
`HAL src/security/exo_hook.rs` or alter its private authority contract.

Philium owns trusted global/project configuration, explicit project consent,
settings UI, effective-config delivery and audit presentation. Extend the
shared builder in `src-tauri/src/providers.rs:357-360`, launch isolation in
`src-tauri/src/hal.rs:103-127`, and settings RPC UI at
`src/screens/settings.jsx:593,622`. Smallest HAL interface: trusted resolved
hook definitions in launch config, structured lifecycle input/output and hook
status events. A gateway-only implementation cannot synchronously cover local
tool dispatch (`HAL src/agent/runtime.rs:3024-3029`).

## Proposed design

1. Add a separate trusted `user_hooks` schema: stable ID, lifecycle event,
   optional tool matcher, argv, timeout and enabled flag. Resolve global and
   project definitions deterministically, show provenance and require consent
   before enabling repository-supplied commands. Agents must not register hooks
   or enable a changed project hook during a running session.
2. Dispatch `session_start`, `before_tool`, `after_tool` and `turn_end` once at
   their actual lifecycle boundaries. Include session, turn and tool-call IDs,
   cwd and bounded event data on stdin. Specify subagent inheritance explicitly.
   Run after-tool on success, denial, tool failure and cancellation with a status
   field. Never recursively dispatch hooks for hook subprocesses.
3. Use a versioned JSON reply with optional bounded context and a before-tool
   veto. Context is untrusted data, never a new system instruction. User hooks
   can further restrict execution, never bypass mandatory sandbox, Exo or
   permission checks. Define whether after-tool context applies to the next
   model request, and reject veto fields on events where blocking is impossible.
4. Execute commands in the agent's sandbox and cwd with an allowlisted clean
   environment, no provider/gateway/desktop tokens and no readable credential
   files. Explicitly deny HAL private configuration/login paths while preserving
   agent workspace grants. Bound stdin/stdout/stderr, concurrency and wall time,
   kill descendant processes on timeout/cancel and redact displayed diagnostics.
   Before-tool failures fail closed. Surface other hook failures visibly without
   masking the original tool/turn outcome.
5. Persist effective-config identity and hook outcomes, expose configuration and
   bounded diagnostics in Settings and agent activity. No dependency, model,
   fingerprint or price literals are needed. Any future runtime dependency must
   follow `AGENTS.md:5-7` rather than introducing stale pins.

## Acceptance checks

These are required future checks, not tests executed during grounding.

- **Running app workflow:** configure a global before-tool hook and consent to a
  project hook. Start an agent, request a specific file write, verify a veto
  leaves the file unchanged and the UI explains it. Permit the same operation,
  verify it succeeds, observe after-tool output and ask a second question that
  demonstrates bounded hook context reached the model. Restart the app and
  verify global/project precedence and consent persist.
- In the app, verify session-start and turn-end run once, including a second
  turn, failed tool, permission denial, cancelled turn and subagent. Disable a
  hook and confirm no command runs. Edit project config and confirm renewed
  consent is required, without automatic execution on merely opening a repo.
- Use canary secrets in provider, gateway and desktop credentials. A hook must
  not retrieve them through env, private config, login files or diagnostics.
  Attempt outside-workspace writes and forbidden network requests under the
  agent's strict policy. Confirm denial and peer-agent isolation.
- HAL regression tests should cover built-in and MCP dispatch, existing Exo
  hard denies despite hook allow, context caps, malformed replies, timeout,
  process-tree cleanup, cancellation and no-hook behavior. Check hook completion
  events and outcome persistence, not only command exit status.

## Dependencies and risks

- I5/I6 affect proving equivalent filesystem/network isolation on supported
  platforms. A3 must not claim secure hooks where the agent sandbox is missing
  (`src-tauri/src/agents.rs:789-795`; `HAL src/tools/shell.rs:267`).
- I4 overlaps credential-file isolation: the generated config already contains
  a gateway token (`src-tauri/src/hal.rs:103-105`). Environment scrubbing alone
  does not meet A3's credential requirement.
- A2 and A1 should share lifecycle ordering with hooks rather than bypassing
  the dispatch seam (`HAL src/agent/runtime.rs:3024-3029`). This is proposed
  integration guidance, not a dependency on those features shipping first.
- Ranking implication: keep A3 a real gap, but not a missing security guard.
  Preserve existing Exo fail-closed behavior (`HAL src/agent/runtime.rs:2875-2895`)
  and scope implementation as a separate automation feature.

## Size

**L.** Cross-repo lifecycle integration, consent UI and safe credential-isolated
subprocess supervision are needed, despite existing dispatcher and policy seams.
