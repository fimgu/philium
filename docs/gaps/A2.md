# A2: Todo/plan tool and plan mode

## Verdict

**Partly true.** The missing Philium plan-mode integration is confirmed: its
message builder sends text, images and browser consent, but no `plan` flag
(`src-tauri/src/agents.rs:1328-1343`). However, HAL already implements enforced
per-turn plan mode, including an HTTP field, tool filtering and dispatch refusal
(`HAL src/server/sessions.rs:256-258,399-400`;
`HAL src/agent/runtime.rs:1996-1999,2609-2618`). This is not a new HAL permission
engine project. The visible-task-list claim is overstated: Philium already has
persistent, agent-accessible board tasks, but not a dedicated conversation-local
checklist (`src-tauri/src/board.rs:26-58,69-79`;
`src-tauri/src/mcp.rs:207-217`). HAL's built-in registry contains no todo tool;
its `task` tool delegates work instead (`HAL src/tools/mod.rs:293-315`;
`HAL src/tools/task.rs:1,29-32`).

All HAL paths below are relative to `~/Developer/hal`; Philium paths are relative
to this repository. Findings are source-grounded, not runtime acceptance results.

## Current state

- HAL advertises `plan_mode_supported` in session details, defaults the message
  flag to false, and transfers it into `UserInput`
  (`HAL src/server/sessions.rs:166,256-258,399-400`).
- A plan turn exposes only `read`, `glob` and `grep`; dynamic MCP refresh is
  disabled for that turn. Calls outside the filtered registry return an unknown
  tool error (`HAL src/agent/runtime.rs:1996-1999,2015-2019,2609-2618`).
- Existing regression source attempts write, shell and subagent calls under
  AutoAllow and checks they do not create files or children. It also checks that
  a subsequent ordinary turn regains write tools. This is evidence of test
  coverage, not a test run in this grounding pass
  (`HAL tests/e2e.rs:266-308`).
- HAL's guard is **turn-local**, not an approval latch: a later non-plan request
  can execute without approving a stored plan
  (`HAL src/agent/runtime.rs:1997`; `HAL tests/e2e.rs:299-307`).
- Philium has persisted board task ownership, progress/playbook steps, task
  events and change broadcasts, plus MCP create/claim/update/submit tools. Those
  represent workspace work coordination rather than a separate per-conversation
  todo protocol (`src-tauri/src/board.rs:26-58,69-79`;
  `src-tauri/src/mcp.rs:207-217`).
- The existing UI transport can carry additional state: agent events arrive over
  HAL SSE and are batched to `agents:events`; the agent screen reloads saved
  events and merges live ones (`src-tauri/src/agents.rs:874-892,929-950`;
  `src/screens/agents.jsx:377-399`). Conversation folding currently handles
  generic tool lifecycle events (`src/ui/conversation.jsx:20-54`).
- Existing permission controls distinguish Ask, AutoAllow and AutoDeny, not a
  planning workflow (`HAL src/security/permissions.rs:40-50`). Philium broadly
  allows its MCP tools while denying HAL shell execution, so prompt-only
  planning would not be a security boundary
  (`src-tauri/src/agents.rs:193-200`).

## Where the fix lives

**Both**, with substantial reuse of HAL's existing primitive.

- Philium: `src-tauri/src/agents.rs` for capability checking, durable plan state
  and every send path; `src-tauri/src/mcp.rs` plus a small owned module for todo
  validation/storage/events; `src/screens/agents.jsx` and
  `src/ui/conversation.jsx` for plan controls and checklist rendering. These are
  the current send, MCP and presentation boundaries cited above.
- Small HAL change: `src/agent/runtime.rs` must admit one explicitly trusted
  checklist-state tool in plan mode without admitting arbitrary MCP tools.
  `src/server/sessions.rs` should expose that capability. Today's three-tool
  whitelist excludes Philium's entire MCP toolset
  (`HAL src/agent/runtime.rs:1998,2018`). No replacement permission layer needed.

## Proposed design

1. Add a bounded checklist tool with stable item IDs, pending/in-progress/done
   statuses, revision checking and an agent/session-scoped snapshot. Persist
   atomically in Philium SQLite and emit a post-commit change event. Keep board
   tasks distinct; optionally link a checklist to a board task.
2. Render the latest snapshot above the conversation, with progress and collapse
   controls. Load the snapshot on open/reload and merge revisioned updates rather
   than inferring authoritative state from model prose or partial tool output.
3. Add explicit Plan / Execute controls. Persist a pending plan revision and
   approval state server-side. While pending, force `plan:true` on all human,
   queued, retry and automatic sends. Do not let model text, MCP arguments or
   a raw `agents.send` override unlock execution.
4. Query HAL's advertised capability before planning. Fail closed with an
   actionable message if unsupported. User approval binds to the displayed plan
   revision and authorizes a separate execution request. Reject stale approval;
   keep a rejected/revised plan locked. Clearly distinguish file read-only from
   allowed checklist metadata persistence.
5. Extend HAL with a narrowly identified trusted checklist adapter usable in
   planning. Validate tool identity and implementation, not just an alias named
   `read` or `todo`; never enable general MCP, shell, delegation or browser tools.
   Alternatively ship planning without checklist updates first, explicitly
   documenting that reduced scope rather than claiming full A2 completion.
6. Keep existing resource permissions and strict-mode rules in force after user
   approval. Resolve all runtime capabilities dynamically, with no pinned HAL
   version, model ID, client fingerprint or price (`AGENTS.md:5-7`).

## Acceptance checks

These are required future checks, not executed in this documentation task.

- In the running Philium app, ask an agent to investigate a real workspace in
  Plan mode. Observe a streamed checklist, successful source reads and a visible
  pending plan. Ask it to write a file, run shell, delegate and use mutating MCP
  or browser tools. Verify rejection and unchanged workspace/external state,
  even under AutoAllow; retain redacted request/event evidence.
- Reload the view and restart the app while approval is pending. Verify the
  checklist and plan revision survive, the lock remains, and queued/automatic
  follow-ups cannot execute. A second agent/session must not change or approve
  the first agent's plan.
- Reject, revise, then approve the displayed revision in the running app.
  Verify stale approval is rejected, only explicit current approval unlocks the
  next request, and execution updates checklist items. Verify a second query,
  stop/resume and reconnect retain the intended state without peer leakage.
- Add backend tests for validation, revision conflicts, ownership, atomic
  persistence and all send-path locks; frontend tests for replay/live merge and
  untrusted labels. Run applicable HAL plan regressions plus forged tool-name,
  MCP refresh and unsupported-server cases before feature acceptance.

## Dependencies and risks

- U4 steering intersects queued sends: a new message must not silently exit the
  persisted plan lock (`src-tauri/src/agents.rs:1346-1350`). U5 history/replay
  intersects restoring checklist snapshots (`src/screens/agents.jsx:377-399`).
- A3 future hooks must not bypass the existing plan whitelist. The broad MCP
  permission makes a general MCP exception unsafe
  (`src-tauri/src/agents.rs:195`; `HAL src/agent/runtime.rs:1998`).
- Confirm runtime HAL capability, not merely the local checkout: the current
  request omits `plan`, and the capability is server-advertised
  (`src-tauri/src/agents.rs:1328-1343`; `HAL src/server/sessions.rs:166`).
- Ranking changes: downgrade the claim of missing HAL planning infrastructure.
  The main remaining work is Philium workflow/state integration plus a narrow
  checklist exception, not a fresh security subsystem (evidence above).

## Size

**L** for complete A2: durable approval enforcement across send paths, persistent
checklists, UI/replay and a small upstream capability change. A plan-only toggle
is smaller but does not satisfy checklist persistence or approval gating.
