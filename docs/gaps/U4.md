# U4. Mid-run steering

## Verdict

**Verified.** Busy submissions use the durable Philium queue, not mid-turn
input (`src/ui/conversation.jsx:975`, `src/screens/agents.jsx:498-513`).
HAL's message endpoint starts a new turn and its session lock rejects a second
turn as busy (`hal/src/server/sessions.rs:388-417`,
`hal/src/agent/runtime.rs:1414-1431`, `hal/src/session/mod.rs:412-424`).
The missing HAL interface in the register is therefore a real prerequisite,
not just a hidden composer control (`docs/GAPS.md:155-159`).

## Current state

- The full conversation composer queues on Enter while busy, shows queued
  messages with edit/remove controls, and separately offers Stop
  (`src/ui/conversation.jsx:975-1002,1084-1099`). Agent detail wires those
  controls to queue RPCs and cancellation; a send/busy race falls back to
  queueing (`src/screens/agents.jsx:498-513,674-677`). The compact agent card
  also queues while busy (`src/screens/agents.jsx:759-771`).
- Queue entries are persisted with text/images, listed oldest first, joined
  into one user message, and deleted only after HAL accepts delivery.
  Delivery waits for Philium state `idle`, so it cannot steer a running turn
  (`src-tauri/src/agents.rs:1347-1395,1767-1792`). Existing queue tests cover
  ordering, taking an item back, and retention while running
  (`src-tauri/src/agents.rs:2391-2407`).
- Sending currently posts text/images and browser availability to HAL's
  `/sessions/{id}/messages`; there is no steering mode in that request
  (`src-tauri/src/agents.rs:1329-1344`,
  `hal/src/server/sessions.rs:248-271,388-417`). Stop cancels the active turn
  and denies pending permission waits, rather than delivering new input
  (`hal/src/session/mod.rs:431-440`).
- HAL already reloads persisted history each model iteration. Tools run
  sequentially except consecutive subagent calls, which run as a concurrent
  batch; results are persisted before the next iteration
  (`hal/src/agent/runtime.rs:2015-2046,2335-2424`). This supplies a useful
  insertion boundary, but not an admission/acknowledgement API.

HAL paths above are relative to `~/Developer/hal`; all other paths are
relative to Philium. Evidence is a source inspection on 2026-11-23, not a
running-app acceptance result.

## Where the fix lives

**Both.** HAL needs a session-scoped input admission primitive and turn-loop
consumption in `src/server/sessions.rs`, `src/session/mod.rs`, and
`src/agent/runtime.rs`, with durable delivery events in its session storage.
Philium needs an `agents.steer` RPC in `src-tauri/src/agents.rs`, delivery-state
rendering in `src/ui/conversation.jsx`, and wiring in
`src/screens/agents.jsx`. These are the existing ingress, execution, queue,
and composer seams cited above. HAL remains read-only for this grounding task
(`docs/LANES.md:13`, `docs/gaps/README.md:10-17`).

## Proposed design

1. Preserve Queue as the default. Add an explicit **Steer at next tool
   boundary** action to busy composers, including compact cards. Do not
   implement steering as Stop followed by Send.
2. Add a HAL authenticated session endpoint accepting a client-generated
   idempotency key, expected active turn ID, text, and validated images.
   Return a stable receipt with `pending`, `applied`, or explicit rejection.
   Advertise capability at runtime so older HALs show Queue only.
3. Persist admitted steering separately from ordinary history. The active
   turn drains admitted entries in admission order into user-role history at
   the next safe tool boundary, emitting receipt/turn-linked events. Do not
   mutate a provider request already streaming or restart in-flight tools.
4. Define boundary precisely: after the executing tool or concurrent subagent
   batch returns, before another already-planned tool starts. If steering
   arrives during a multi-call response, close remaining unexecuted tool
   calls with explicit skipped results, then replan with the new user input.
   This avoids executing stale queued tool intent or leaving unmatched calls.
5. At terminal completion, cancellation, or restart, retain unapplied receipts
   visibly for explicit queue/retry. Atomically serialize terminal transitions
   against admission. Never silently report an unapplied message as delivered,
   duplicate it on retries, or promote user text to system instructions.
6. Show pending versus applied steering separately from ordinary queued
   messages. Keep existing queue edit/remove and default delivery semantics.

## Acceptance checks

Proposed checks, not executed here, per `docs/gaps/README.md:15-22`:

- In the running app, start a real agent doing a visible multi-tool task.
  Submit an ordinary message while busy and observe it remain queued until
  turn completion. Repeat with Steer: observe a pending receipt, the current
  tool finish, an applied transcript event, and the next model request follow
  the changed instruction before any remaining obsolete tool executes.
- Exercise two sequential tool calls and a concurrent subagent batch. Verify
  complete result pairing, no rerun of completed tools, and the documented
  batch boundary. Verify both full agent view and compact card controls.
- Submit two steering inputs plus images, retry an acknowledgement after a
  lost connection, and inspect persisted history/events for admission order,
  preserved attachments, and exactly one application per receipt.
- Race admission with completion, Stop, permission waiting, and app/HAL
  restart. Verify explicit retained/rejected status, no accidental new turn,
  and no bypass of permission decisions. A second agent must remain isolated.
- Add HAL API/runtime integration checks for busy versus idle admission,
  invalid/stale turn IDs, session isolation, terminal races and idempotency.
  Re-run existing queue regressions and test older-HAL capability fallback.

## Dependencies and risks

- Requires upstream HAL work before the Philium control can be functional;
  the existing new-turn lock alone cannot provide it (HAL references above).
- A2 plan mode and A7 compaction must preserve the active turn's policy and
  admitted user input. Steering must not escalate browser/permission grants;
  those are currently turn input fields (`hal/src/server/sessions.rs:256-270`).
- Main risks are stale multi-tool intent, concurrent batch latency, and
  duplicated/lost inputs around terminal races, motivating the explicit
  boundary and durable receipts above. No other gap is a prerequisite.
- No version, model or price literal is needed. Negotiate capability from the
  running HAL, respecting runtime resolution rules (`AGENTS.md:5-7`).

## Size

**L.** Cross-repository durable admission, protocol-safe tool interruption,
terminal-state race handling and two composer surfaces, not just a UI toggle.
