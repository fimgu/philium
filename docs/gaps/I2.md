# I2: Signing and notarization

## Verdict

**Verified for release signing, partly true as phrased.** Philium explicitly
selects the ad-hoc identity (`src-tauri/tauri.conf.json:25`). The claim that
this establishes weak agent sandbox entitlements conflates two mechanisms:
agent confinement uses generated Seatbelt profiles passed to `sandbox-exec`,
not an application entitlement (`src-tauri/src/sandbox.rs:291-324`).
No downloaded artifact or Gatekeeper behavior was tested in this grounding.
Tauri documents that ad-hoc signing does not remove the need for a user
security override (external source [T1], checked 2026-11-23).

## Current state

- The bundle includes app/DMG, MSI and Linux targets, plus the HAL sidecar;
  its macOS block specifies only an ad-hoc identity and minimum OS
  (`src-tauri/tauri.conf.json:20-25`). No explicit entitlement file or
  notarization configuration appears in that block. This does not prove
  hardened runtime is disabled, since bundler defaults must be checked.
- Pilot changes the product identifier and window, not signing
  (`src-tauri/tauri.pilot.conf.json:1-5`); its build command emits an app
  bundle (`package.json:9`). It is not a separate release-signing solution.
- Existing checks verify signature integrity with `codesign --verify --deep
  --strict`, and check that HAL is bundled, but these checks do not assert
  Developer ID identity or a notarization ticket
  (`scripts/check-pilot.py:12-20`, `scripts/check-acceptance.py:30-36`).
- Sidecar staging builds HAL from a sibling checkout and copies its executable
  into Philium, with a source revision printed to stdout
  (`scripts/sidecar.sh:4-11`). At runtime Philium locates HAL beside its own
  executable (`src-tauri/src/hal.rs:59-70`). Release validation must therefore
  include that nested executable, not only the app wrapper.
- HAL's separate native macOS packaging also ad-hoc signs its helper and
  wrapper (`../hal/desktop/scripts/macos.sh:14-17,40-42`). That script is not
  the Philium staging path (`scripts/sidecar.sh:7-10`).
- Read-only `git ls-files .github` returned no tracked workflow paths in either
  repository. This supports the I1 premise (`docs/GAPS.md:182-186`), but says
  nothing about any external release service or untracked CI configuration.

## Where the fix lives

**Philium-only.** Own the release job, Tauri release configuration, sidecar
provenance and artifact checks in Philium. No HAL API change is required:
Philium already builds and stages its executable (`scripts/sidecar.sh:7-10`).
HAL's standalone app signing would be a separate upstream packaging task
(`../hal/desktop/scripts/macos.sh:14-17,40`).

## Proposed design

1. Keep local ad-hoc builds possible, but add a protected release configuration
   that cannot fall back to `-`. Supply the Developer ID identity from CI;
   Tauri supports its signing identity environment variable [T1]. Explicitly
   validate the effective release configuration before publishing.
2. Use a short-lived CI keychain and protected signing/notarization secrets.
   Import the certificate only for trusted release jobs, never fork PRs.
   Configure Tauri's supported notarization credentials, wait for acceptance,
   staple the distributable and validate the ticket [T1]. Delete the temporary
   keychain and credential files on success and failure. Never log secrets.
3. Inventory nested executables, sign them and the final app with the intended
   identity, and verify hardened-runtime and minimal entitlement requirements
   against current Tauri/Apple guidance. Do not add broad JIT or unsigned-memory
   exceptions speculatively. Preserve Seatbelt behavior as a separate contract
   (`src-tauri/src/sandbox.rs:291-324`).
4. Build and attest the HAL source revision and target alongside Philium's
   revision, extending the provenance already printed by staging
   (`scripts/sidecar.sh:5-11`). Publish only after all artifact checks pass.
5. Record an explicit Windows decision before shipping MSI: provision a trusted
   Windows signing service and timestamp verification, or withhold public MSI
   publication until provisioned. MSI is currently a configured target
   (`src-tauri/tauri.conf.json:22`), not evidence of an existing signed release.

## Acceptance checks

These are proposed checks, **not executed** in this documentation-only task.

- Release job: reject absent/wrong identity, ad-hoc signatures, failed or pending
  notarization, invalid staples and unexpected nested executables. Inspect the
  final app and HAL identity/team, runtime flags and entitlements. Verify
  signature integrity, Gatekeeper assessment and staple validity on the exact
  published artifacts. Existing integrity-only checks are insufficient
  (`scripts/check-pilot.py:17-20`).
- Real macOS workflow: download the published DMG through a browser onto clean
  supported Apple Silicon and Intel machines, retain quarantine, mount, drag
  to Applications and launch normally without a security override. Configure
  a provider, complete a fresh query and second query, run an agent file/tool
  action, stop it, quit and reopen. Observe actual HAL launch and cleanup,
  denied forbidden file access and allowed workspace access under Seatbelt
  (`src-tauri/src/hal.rs:59-70`, `src-tauri/src/sandbox.rs:316-324`).
- Repeat offline first launch after downloading the stapled artifact. Keep
  fresh-download Gatekeeper checks separate from synthetic Pilot checks,
  whose documented network/model dependencies are local stand-ins
  (`scripts/check-acceptance.py:6-16`).
- Windows decision: if MSI ships, download/install on clean Windows, inspect
  executable and installer signatures/timestamps, launch and complete a query.
  Otherwise prove release publication excludes MSI and states the restriction.
- Confirm fork PRs cannot read signing secrets and teardown removes CI keychain
  material after both failed and successful release attempts. Retain redacted
  identity/notary evidence tied to artifact digests and source revisions.

## Dependencies and risks

- I1 supplies release automation; I3 update authentication is a separate layer,
  not replaced by Developer ID signing (`docs/GAPS.md:182-198`).
- Coordinate I5 before promising Windows/Linux support: those targets are
  configured, while the gap separately calls for platform confinement
  (`src-tauri/tauri.conf.json:22`, `docs/GAPS.md:210-215`).
- Certificate enrollment, renewal and CI credentials are operational blockers
  until provisioned. Their existence was not inferred from repository files.
- Resolve current tooling through trusted registries and current documentation.
  Keep any unavoidable security pin exclusively in `src-tauri/src/pins.rs`
  with a maintenance reason (`AGENTS.md:5-7`).

## Size

**M.** Packaging and CI integration rather than a HAL API change, with external
credential provisioning and clean-machine acceptance dominating elapsed time
(the owned boundary is `scripts/sidecar.sh:4-11` and
`src-tauri/tauri.conf.json:20-25`).

External reference [T1]: Tauri, “macOS Code Signing”, official documentation,
`https://v2.tauri.app/distribute/sign/macos/`, checked 2026-11-23.
