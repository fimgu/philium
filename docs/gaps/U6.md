# U6. Native OS notifications

## Verdict

**Verified.** Native delivery is missing: the dependency manifest has no notification
plugin, the Tauri builder goes directly to setup, and the main-window capability
only grants core permissions (`src-tauri/Cargo.toml:9-38`,
`src-tauri/src/main.rs:339-342`, `src-tauri/capabilities/default.json:1-5`).
The existing substitute is real: approval counts in navigation and state-transition
Web Audio chimes (`src/main.jsx:149-150`, `src/lib/store.js:176-183`).
The audit's background-only implication is overstated: the sound path checks its
mute preference but not window focus or Do Not Disturb (`src/lib/sound.js:38-59`).

## Current state

- Philium compares agent-list snapshots, skips the initial snapshot, then chimes
  for waiting, done/running-to-idle and failed (`src/lib/store.js:160-188`). This
  is useful existing behavior, not a native notification delivery layer.
- Failure classification cannot be copied from this snapshot heuristic: both
  `turn.failed` and `assistant.completed` map to idle, so a running-to-idle failure
  can take the done-sound branch (`src-tauri/src/agents.rs:1066-1076`,
  `src/lib/store.js:179-182`). Cancellation also maps to idle at the same backend
  location and must not become a completion notification.
- The backend already consumes HAL SSE events, tracks their sequence, applies
  them individually, then batches frontend delivery (`src-tauri/src/agents.rs:915-932`).
  It emits approval events and separately handles/logs turn failures and successful
  completion (`src-tauri/src/agents.rs:1260-1280,1300-1307`).
- HAL already supplies the necessary primitives: event sequence identity
  (`../hal/src/events.rs:13-14`), completion/failure/cancellation with turn IDs
  (`../hal/src/agent/runtime.rs:1636-1649`), and approval request emission
  (`../hal/src/session/mod.rs:533-552`). No new HAL event is needed.
- Navigation already supports route parameters, and Agents selects from `params().id`
  (`src/lib/nav.js:8-13`, `src/screens/agents.jsx:1120`).

## Where the fix lives

**Philium-only.** Add an owned notification module beside the existing agent
consumer and call it from the individual event handling path, not from agent-list
polling (`src-tauri/src/agents.rs:919-922,1260-1307`). Wire plugin initialization
in `src-tauri/src/main.rs:339-342`, dependency declaration in
`src-tauri/Cargo.toml:9-38`, and only the required capability additions in
`src-tauri/capabilities/default.json:1-5`. Frontend activation should reuse
`go("agents", { id })` and the existing ID selection contract
(`src/lib/nav.js:9-13`, `src/screens/agents.jsx:1120`). HAL remains read-only
(`docs/LANES.md:13`).

## Proposed design

1. Install the current compatible Tauri notification plugin, resolving its release
   from the registry during implementation. Verify its actual desktop activation
   API before choosing click routing. If it cannot carry activation context on a
   supported OS, add the smallest native adapter rather than claiming delivery
   alone meets click-through. No stale SDK/model/version literals in product code
   outside the prescribed pins module (`AGENTS.md:5-7`).
2. Normalize `assistant.completed`, `turn.failed`, and `permission.requested` into
   typed alerts. Use agent/session identity plus sequence for replay deduplication,
   and request ID for approval identity. Preserve failure versus success and ignore
   cancellation. Proposed inputs already exist in the event path cited above.
3. Keep delivery in the backend so minimizing the webview does not make frontend
   polling the authority. Persist a notification high-water mark separately from
   SSE consumption progress and initialize it without notifying historical events.
   Define restart behavior explicitly, avoiding replay storms while not silently
   consuming fresh live events during permission changes.
4. Request notification permission through an explicit user action. Provide an
   enable/disable control and clear denied-permission fallback. Suppress external
   alerts while the app is focused. Submit ordinary-priority notifications to the
   OS, with no DND bypass, critical alerts or parallel Web Audio fallback in the
   background. Reconcile the existing sound setting with this policy so a native
   notification suppressed by DND cannot still produce an app chime.
5. Store only a validated agent ID and event identity as activation context. On
   click, restore/focus the main window and route to that agent. Queue activation
   until the frontend is ready. Handle deleted agents with a safe Agents fallback.
   Never auto-approve a tool or execute notification-provided text.
6. Default lock-screen content to generic finish/failure/approval labels. Do not
   copy model output, shell commands, paths, error bodies or credentials into OS
   notification history. Coalesce rapid alerts per agent without hiding pending
   approvals; make repeated failure/retry behavior explicit.

## Acceptance checks

These are implementation acceptance requirements, not results of this docs-only pass.

- Declare supported macOS, Windows and Linux desktop rows before implementation
  validation. On each supported platform, run the packaged app with OS permission
  allowed: start a real agent, background/minimize Philium, complete a turn, induce
  a real failure, and trigger an actual approval request. Observe one correctly
  typed native alert each, with no completion alert for cancellation.
- Click each alert from the OS UI. Verify restoration and exact-agent selection,
  including while another agent is selected. Verify approval remains pending until
  the user approves inside Philium. Repeat after a frontend reload and test an
  expired/deleted-agent target.
- Repeat focused, muted, notification-disabled, permission-denied and OS DND/focus
  modes. Check native visual/audio behavior and absence of bypassing Web Audio.
  Restore OS settings afterward. Test permission revocation without restarting.
- Run two agents concurrently, reconnect the event stream, reload the UI and
  restart the app. Verify no cross-agent routing, historical replay or duplicate
  alert. Verify new events still notify after reconnect and permission recovery.
- Add normalization/dedup/focus tests covering idle-on-failure, cancellation,
  repeated approval, sequence replay, missing IDs and deleted agents. Run the
  applicable Rust/frontend tests and production build, but do not substitute them
  for the desktop workflows above. Keep unsupported or blocked rows visible.

## Dependencies and risks

- No HAL change or agent-core gap dependency: current event types already distinguish
  all required outcomes (`../hal/src/agent/runtime.rs:1636-1649`,
  `../hal/src/session/mod.rs:533-552`).
- The existing done-chime misclassification is a concrete adjacent UX defect to fix
  within U6, not a reason to implement notifications on state snapshots
  (`src/lib/store.js:179-182`, `src-tauri/src/agents.rs:1073-1075`).
- I2 packaging/signing may affect distributable identity and permission validation;
  its stated scope is signing/notarization (`docs/GAPS.md:188-192`). Native
  activation support and platform environments are implementation validation risks,
  not established capabilities of an uninspected plugin release.
- New capabilities must stay least-privileged, and activation must not become an
  approval bypass. Existing capability scope is core-only
  (`src-tauri/capabilities/default.json:4`); runtime resolution follows `AGENTS.md:5-7`.

## Size

**M.** HAL already exposes the events, but reliable native activation, permission,
focus/DND policy, replay deduplication and desktop acceptance make this more than
adding a toast call (`src-tauri/src/agents.rs:915-932,1260-1307`).
