# I4: Secrets in plaintext JSON

## Verdict
**Verified, with existing containment and a confirmed UX reason.** The vault is
read as text and serialized as JSON without encryption
(`src-tauri/src/secrets.rs:45-65`). `keyring` remains a dependency
(`src-tauri/Cargo.toml:20`), but the storage module explicitly avoids Keychain
access prompts (`src-tauri/src/secrets.rs:1-11`). This is not a world-readable
file: writes enforce a 0700 directory and 0600 file
(`src-tauri/src/secrets.rs:58-65`). An unsandboxed same-user process can read it,
as the existing test explicitly demonstrates (`src-tauri/src/secrets.rs:131-137`).

## Current state
- A process-wide lazy map caches credentials. Writes replace the file atomically
  after syncing it, and update the cache only after successful persistence
  (`src-tauri/src/secrets.rs:21-24,54-74,83-96`). Invalid JSON is not treated as an
  empty vault (`src-tauri/src/secrets.rs:45-50,153-157`).
- Provider keys and OAuth credentials share this store. The OAuth implementation
  is misleadingly named `Keychain`, but delegates to the JSON vault
  (`src-tauri/src/providers.rs:132-141`, `src-tauri/src/oauth.rs:177-187`). MCP
  environment/header secrets and release credentials also use the same API
  (`src-tauri/src/mcp_servers.rs:175-190`,
  `src-tauri/src/release_intake.rs:420-433,560-569`).
- Preview builds refuse reads and writes (`src-tauri/src/secrets.rs:36-39,76-85`).
  The filesystem guard blocks the secrets directory
  (`src-tauri/src/access_fs.rs:95-101`). Seatbelt denies vault reads and writes
  for trusted agents, but falls back to unwrapped argv without an available
  profile (`src-tauri/src/sandbox.rs:269-305`).
- **Why Keychain was rejected:** source comments say access prompts, not sandbox
  access or headless use (`src-tauri/src/secrets.rs:1-11`). History confirms the
  sequence: `21aa06a` changed to one cached Keychain item per run, documenting
  prompts per item/read from an unrecognized build (historical
  `src-tauri/src/secrets.rs:1-7`). `27143ff` replaced that with a private file.
  `fa81f9a` removed automatic reads/migration of legacy Keychain entries. Current
  code leaves those entries untouched and requires sign-in when file credentials
  are absent (`src-tauri/src/secrets.rs:10-11`). Simply restoring per-secret
  Keychain reads would recreate the rejected experience.
- **HAL boundary:** HAL accepts supplied model API keys
  (`../hal/src/config.rs:506-518`). Philium supplies its gateway token and URL,
  not provider keys, and disables login discovery
  (`src-tauri/src/providers.rs:289-309,354-360`). No HAL storage change is needed.

## Where the fix lives
**Philium-only.** Implement storage/migration in `src-tauri/src/secrets.rs`, plus
explicit unlock/error UI and startup coordination. Preserve provider/OAuth
call sites and gateway-only credential delivery described above. Keep the
existing secrets directory path because filesystem guards and sandbox profiles
use it (`src-tauri/src/access_fs.rs:98-101`,
`src-tauri/src/sandbox.rs:269-278`). HAL stays read-only.

## Proposed design
1. Store a versioned authenticated-encryption envelope in the private directory,
   with one randomly generated vault key held in the OS credential store. Cache
   the unlocked key/map for the app lifetime, not one OS lookup per credential.
   Use a maintained authenticated-encryption library and platform backend,
   resolving dependency versions at implementation time.
2. Make unlock an explicit, coalesced user operation with a visible locked state.
   Do not trigger prompts from background agent spawning, provider polling or
   missing-secret lookups. A denied/unavailable/locked OS store fails closed
   with an actionable retry, never a plaintext fallback. Validate whether a
   stable signed app identity prevents repeat prompts across releases before
   claiming prompt fatigue solved.
3. Migrate only the current plaintext file after successful unlock: validate the
   entire map, establish the key, write and sync the encrypted replacement,
   verify decryption/content, then remove the plaintext source and sync the
   directory. Make interruption recovery deterministic and idempotent. Retain
   the original on any failure, report migration pending, and do not silently
   resume normal plaintext writes. Secure erasure of old backups is not promised.
4. Preserve preview isolation, permission hardening, failed-write cache behavior
   and corrupt-file refusal. Expose locked/storage failure separately from
   absent credentials. Current `get` collapses errors into `None`, while `delete`
   discards persistence errors (`src-tauri/src/secrets.rs:76-108`), so propagate
   meaningful errors through affected callers instead of reporting false success.
5. Do not automatically scan old per-secret Keychain entries. Offer a separate
   explicit recovery/import action only if required, preserving the current
   no-background-Keychain-read decision (`src-tauri/src/secrets.rs:10-11`).

## Acceptance checks
These are implementation acceptance requirements, not tests executed in this
read-only grounding pass.
- Unit/integration coverage: first run, encrypted reload, all secret namespaces,
  missing key, unavailable backend, denied unlock, corrupt envelope, tampering,
  nonce uniqueness, failed save/delete, and preview isolation. Verify cache and
  disk do not diverge and no plaintext fallback is created.
- Migration fixtures: valid/invalid JSON, empty vault, crashes before/after key
  creation and replacement, failed verification, retry, and concurrent startup.
  Verify no plaintext source/temp file remains after successful migration and
  no source data is lost after failed migration.
- Keep `vault_is_private_and_hidden_from_agents` and adapt its on-disk assertions
  to encrypted storage, retaining real subprocess denial and permission checks
  (`src-tauri/src/secrets.rs:116-157`). Verify strict and trusted agent paths,
  including alternate path spellings.
- Real running-app workflow on macOS, Windows and Linux: start with a disposable
  plaintext vault, explicitly unlock/migrate, verify provider and OAuth-backed
  requests, run a second agent/query without extra prompts, restart and unlock,
  rotate and delete credentials, then verify persisted deletion. Include MCP
  credential use. Observe actual OS-store access and inspect app-owned disk
  artifacts for sentinel plaintext without recording real credentials.
- On each platform, cancel unlock and lock/disable the OS store. Confirm clear
  recoverable UI, no silent loss, no request with missing credentials, and no
  background prompt storm. Test an app upgrade under its actual signing identity.
  Keep unavailable platform results visibly blocked, not passed.

## Dependencies and risks
- I2 signing identity is relevant to the historical unrecognized-build prompt
  problem (`21aa06a:src-tauri/src/secrets.rs:1-7`). Encryption alone is not proof
  that the same-user active-process threat is eliminated. Test actual backend
  access control separately from encrypted-file inspection.
- I5 remains separate and important: trusted wrapping can return no profile
  (`src-tauri/src/sandbox.rs:282-305`). Encryption at rest does not replace
  agent isolation or protect keys after legitimate unlock.
- I7 must redact unlock/migration diagnostics. This vault contains more than
  model credentials, including release and MCP secrets (call sites above), which
  increases the migration blast radius. Keep I4 high priority but credit its
  existing private permissions and macOS agent denial rather than claiming no
  protection exists.
- No fixed model IDs, client fingerprints, prices or versions are needed. Follow
  the runtime-resolution policy (`AGENTS.md:5-7`).

## Size
**M.** One central store limits scope, but crash-safe migration, explicit unlock
UX and real OS-backend/prompt behavior across three platforms require more than
swapping a storage call (central API: `src-tauri/src/secrets.rs:76-108`).
