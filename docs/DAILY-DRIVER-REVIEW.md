# Daily-driver decision record, 17 November 2026

**Verdict: candidate, not release approval.** Keep Philium native and local for supervision, editing and review. Make expensive execution a separately admitted resource, not a side effect of creating a conversation. Do not solve this by giving every agent its own VM or by pointing the current kind integration at the user's Kubernetes context.

## Evidence from this checkout and machine

* Baseline `9de28cf`, macOS 26.6.2 arm64, 16 GiB unified memory, 10 logical CPUs. At observation the running `exo-ship` Colima profile was configured for 6 CPUs and 10 GiB; the current runtime had 3 kind clusters and 7 running containers. System swap in use was 3.38 GiB. Allocation is not RSS, swap is system-wide, and a snapshot doesn't attribute blame. These existing resources were not stopped. The Philium ledger had zero active kind clusters: accounting only for its own rows misses this machine's main constraint.
* `~/Developer/exo` has 6,196 tracked paths at `ca5ad617d`. Its Autonomic charts contain CRDs and ClusterRoles. In this checkout Sentinel includes native macOS and Linux service/installer workflows under `deploy/sentinel`; a Pod is not a representative native-host test. A separate canonical Sentinel checkout was not established. Neither codebase was changed.
* The Philium DB previously observed in this session had 1,958,952 `ci_refs` across indexed scopes. That is neither a RAM measurement nor proof every screen loads the DB. The specific problem at baseline is `codeindex::load_view`: it reads all effective refs into Rust strings under the DB connection lock before filtering. Benchmark individual paths and allocation before changing retention or rebuilding an index. Never delete the user's DB as a speed fix.
* SPEC N6 and §10 explicitly promise immediate, uncapped agent starts. This is in tension with the requested interactive machine. Proposed amendment: unlimited **saved work**, limited **simultaneous execution**. HAL processes, build subprocesses, WebViews, node containers and VM overhead need separate accounting.
* Exo already has a cluster devbox execution path (`cli/devbox_cluster.go`) and workspace migration (`cli/devbox_move.go`). However, the installed CLI (`v0.6.38`) says `unknown command "devbox"`. Do not assume it can run source-tree features. Do not automatically migrate a developer home or use a current-context fallback. First validate a matched CLI/server against a named non-production deployment.

## Proposed requirements for owner sign-off

These are targets, **not achieved measurements**. Use a pinned fixture revision/toolchain, the same Mac, and separate cold from warm. Publish machine load, count, p50/p95, peak resident memory, incremental swap, disk growth, error rate and retry count. For responsiveness measure input to usable content, not RPC completion.

## Execution placement and rollout

1. **Local first for interaction.** Reuse workspace metadata; materialize a write worktree only for mutation. Lease CPU-heavy (`build`, `index`, `kind`) resources separately from cheap sessions. One status line: `Queued: local build slot in use` or `Testing on <runner>`. Show details and ownership on demand; do not broadcast warning banners across workspaces.
2. **First remote pilot: offload builds/tests, not HAL or the vault.** A named Exo devbox on an approved dev deployment is the first candidate. An existing dedicated Linux VM is a fallback if the Exo versions don't match, not a reason to deploy a second orchestration platform. Pin a clean SHA and runner image, use short-lived repo-scoped credentials and one job ID per submission. No forwarding host SSH agents, kubeconfigs, provider keys or Docker sockets. Avoid shipping uncommitted edits by default; explicitly approve a patch manifest when needed. Cache only by repo/trust domain + toolchain/lockfile; keep writable outputs private.
3. **Choose isolation by operation, not repo name.** Namespace-only application tests may use a shared non-production cluster with deny-by-default RBAC, egress policy, Pod Security, resource quotas and LimitRanges. Full Exo installation, CRD/controller/RBAC changes, or privileges get a disposable control plane on an isolated VM. Never run privileged nested kind against the shared cluster's host socket. Native Sentinel is a third class, not a namespace.
4. **Persist and reconcile before scaling.** Record owner, immutable target/engine identity, remote UID, SHA, resource class, deadline, heartbeat, log cursor, result and cleanup state. On timeout do not assume deletion succeeded. Export diff + test logs first, keep dirty/unpushed work, delete only exact owned resources, and do not route to another engine after a context switch. Require a kill switch and an agreed spend/concurrency ceiling. Expand to multiple runners only after cancel, reconnect, orphan/peer and soak gates pass.

## Remaining release blockers and safety boundaries

* No durable fleet-wide admission queue for HAL + shell + build workloads. The managed kind cap does not restrict arbitrary shell processes or external launchers. The current implementation counts active clusters in the current kind runtime and Philium reservations, not load across a fleet.
* No enrolled remote destination, remote auth/reconnect/teardown evidence, or native Sentinel acceptance. Resource identity across Docker context changes and all Reaper paths need verification before remote destructive actions. Do not treat a name prefix as a globally unique external identity.
* Selfdev rebuild and application installation are separate. Keep the existing installed app until a tested, explicit install/rollback workflow is available. Guard rejections are not an excuse to relax secret protection.
* No benchmark proving the UI, memory or model accuracy targets above. Inspect visited-but-hidden panes and backend fan-out under a measured workload. Product suite results and local regression logs are not full installed-app acceptance.
* Owner decisions: choose a non-production destination, data boundary (may Exo/Sentinel source leave the Mac for that target?), and actual expected concurrency. Default until then: no remote mutation or billable provisioning. Confirm whether “Sentinel” means the Exo service above or a separate source checkout.
