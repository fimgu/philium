# Review as a first-class Philium workflow

For the proposed one-input release workflow, see [Verify a release PR](RELEASE-VERIFICATION.md). It defines nested PR discovery, orchestration, independent attribution and the private ship decision.

Proposal, 2026-11-18. Baseline inspected: `018b09e`. No changes to runtime, review gate or disclosure policy are implied by this document. See `DAILY-DRIVER-REVIEW.md` for the host constraints and remote-runner pilot.

## Start from the review you already do

Jcode's local `review-pr` skill and `review_gate.py` freeze cases, check the actual head, require per-case observations and hashed artifacts, and distinguish checking evidence from posting approval. Local inspection found 47 packet files. One sampled packet had 17 passed cases and one blocked. Another had five passed, three blocked and two failed. These are packet snapshots, not approval statistics. The useful home-screen question is **what still prevents a decision on this revision?**, not how many agents finished. Lead with the blocker, owner and next action. Preserve the failed attempt even when a rerun passes.

Give Philium a **Review** view within the selected repo, not a new agent for every PR. Opening a review should do no network I/O. Show locally known base/head with freshness, change intent, required workflows, findings and evidence. Fetching the actual PR or posting a decision is a separate attributable action. Never call a cached SHA current just because no network check was allowed.

## Responsibilities and boundaries

1. A trusted local coordinator imports an existing Jcode packet read-only or plans a new review. Pin repo identity, base/head (and merge candidate where relevant), policy version and plan digest. Load mandatory workflow profiles from trusted configuration outside PR control. Changed tests/policies from the candidate are inputs, not the authority for waiving tests. For a new head retain the old packet as history, create a new plan and rerun required acceptance.
2. HAL helps read relevant diffs and propose findings: file/line, user impact, confidence and how to verify. Start with local Git/index; fetch additional context only when needed. Parallelize *different hypotheses*, not copies of the entire prompt: e.g. one reviewer for compatibility, one for ownership/lifecycle, one deterministic runner for the affected integration. With no approved model endpoint use deterministic local planning/checks or a permitted local model. A runner is not necessarily an AI agent.
3. A runner gets a job-scoped capability for a specific source tree/artifact, test, environment, quota, deadline and output destination. Review source is immutable. Agent fixes go on a different branch, return as a new candidate and never rewrite the reviewed snapshot. Write findings and observations append-only. If the control plane disconnects, resume by job ID and log cursor, not by starting the command again.
4. Keep plan, runs, evidence, findings and decision distinct. Each run records actual input and output digests, runner identity, OS/arch, timestamps, method (native/headless/mock), sanitized observation, retained artifact hash and cleanup result. Verdicts distinguish pass/fail/blocked/untested/stale. Runner exit 0 or a hash is not proof of the user outcome. A reviewer inspects the artifact and unresolved findings. Only the authorized human and existing guarded approval path may publish a commit-bound decision. No approval credential on worker machines. Re-check remote PR head before publishing; stale or unreachable means no approval.

## Where to run a case

| Change | Default execution | Evidence necessary for the claim |
| --- | --- | --- |
| Pure code or docs | Local read-only diff plus headless tests in a disposable workspace | Scoped assertions or rendered docs/examples. No cluster and usually no model call. |
| Exo application API or chart values confined to namespaced resources | Local headless first; quota-limited namespace on an explicitly enrolled non-production cluster when integration matters | Real request against the candidate, expected marker/result, disconnect/retry and peer unaffected. Use restrictive RBAC, Pod Security, network policy and isolated secrets. Only admit workloads meeting the cluster's trust policy. |
| Exo CRDs, controllers, admission or cluster-wide RBAC | Dedicated disposable control plane. Local kind only with spare capacity and a dedicated runtime for untrusted code. Otherwise remote kind on an isolated private VM | Install baseline, exercise upgrade, observe reconciliation and failure path, check peer and teardown. Never run nested privileged kind on a shared host socket or infer a target from current-context. |
| Sentinel service/package or Philium desktop lifecycle | Disposable native OS matching the claim. Linux VM for systemd, separate macOS session or VM for app/launchd, matching Windows target when supported | Real install/start/update/restart/uninstall as applicable. For Philium: native picker, session restoration, actual HAL and no window/input on the user's working desktop. Headless coverage is useful but does not pass native rows. |
| Feature in Exo consumed by Sentinel | Synthetic versioned contract fixture by default; then specific pinned producer and consumer artifacts in a private integration job if needed | Old/new supported combinations, intended success and failure. Verify real integration where promised. Grant access to two full source checkouts only if artifacts cannot answer the question and both repos permit the transfer. |

A worktree separates changes, not privileges. A namespace separates names, not all cluster-scoped authority. A company cluster is not implicit permission to publish code to its model vendor. These are three different decisions.

## Confidentiality is independent of execution location

Sketch a local policy per **repo × principal × data class × destination × purpose**, with expiry and revocation. Default deny for unlisted transfers, including to another product. Distinguish fetch from the repository's authorized Git origin, remote execution, model inference, package mirrors and publication of evidence. A private runner grant is not a model grant. Source includes excerpts, diffs, stack traces, filesystem paths, screenshots, symbols, embeddings, transcripts and tool output. A green secret scanner does not declassify proprietary code.

Enforce before retrieval *and* before dispatch. `src-tauri/src/mcp.rs` currently denies history to Strict agents, but a non-Strict `session_search` defaults `repo_only` to false. In `library.rs`, repo filtering is conditional on a resolved project. For review, derive identity from the job capability rather than agent-supplied flags, fail closed on missing project, and prevent shell/file/MCP fallback from accessing a sibling repo or global history. No access by default to other users' caches, logs, Docker sockets, model keys or home folders. Enforce egress on child processes, builds, dependency hooks and the remote host, not just in the LLM gateway. Only reuse caches from the same trust domain; no shared writable cache from untrusted PRs into trusted builds.

Show **who gets what and why** before a new destination is permitted: e.g. “Send these two files at this SHA to private runner A to build”, not “Allow network”. Prefer a pinned artifact or minimal manifest over full checkout. If the only approved path is unavailable, queue or mark blocked; never fall back to a third-party model or a different cluster. Meter outgoing requests, bytes, recipient and denied transfers locally without recording payloads. Retain minimal raw evidence locally with access restrictions and expiry. Publish a separately reviewed redacted summary, never the raw packet by default.

## Ship in this order

1. **Local packet viewer and policy first.** Import existing packets, show tested vs current-known revision and first blocker; no auto-fetch, telemetry, model, cluster or Git writes. Reuse the Jcode checker where compatible instead of duplicating approval logic. Treat imported files as untrusted: schema, size and artifact path containment checks before rendering. Label historical offline results as historical, not approval-ready.
2. **One local executor.** Trusted headless profiles, bounded queue, read-only inspection, independent evidence, deadline, cancellation and owned cleanup. Pilot on one prior passed case and one blocked case. Acceptance: review can open offline, correct mixed verdict is shown, no peer workspace access, user's desktop never gains or loses focus.
3. **One private runner, not a fleet.** Pilot one Exo integration case alongside an unaffected peer. Pin engine/cluster identity and immutable job UID before any delete. Validate quota/denied egress, loss of network, reattach without duplicate, explicit cancel, stale-head rejection, artifact retrieval and cleanup. Where no permitted execution environment exists, leave the row blocked.
4. **Swarm and remote development last.** Add workers only when they reduce time to a verified decision. Allocate model budget, HAL slots and expensive build/kind slots independently. Remote *development* gets a separate, intentionally persistent writable workspace with explicit sync/diff, conflict handling and recovery of unpushed work. Never reuse it as the clean environment that certifies its own output.

Measure median time from review start to first actionable blocker and to a verified verdict, escaped defects and reopened findings, duplicate jobs, peak local memory, and external requests/bytes per review. First privacy regression fixture: unique inert markers for repos A/B. In A's review B's marker must not be retrievable or observable at any test recipient; with no egress grant the test recipient receives zero requests. Test missing repo identity and provider failure explicitly.

Design references: Kubernetes multi-tenancy guidance, GitHub Actions secure use reference, SLSA v1.2 provenance. These inform boundary and provenance choices; they are not claims that Philium already enforces them.

## Team workflow: PRs, nightly bundles and independent findings

**Choose the target once per job.** Offer Local headless, Local kind (explicit capacity reservation), Team staging (a named connection, potentially reached via `mycli connect`), and Disposable private runner (including AWS). Enroll a target before scheduling: pin its identity, authorized repo/artifact, credential lifetime, concurrency and spend ceiling. For EKS, map a dedicated IAM identity to narrow Kubernetes permissions. A trusted allocator creates and expires a per-run namespace; workers may manage only needed resource types inside it. Do not give workers namespace deletion, cluster-wide bindings, secret access outside their namespace or mutations of `mycli`. Kubernetes RBAC grants are additive: a narrow RoleBinding cannot cancel a broader grant. Verify the *effective* permissions, including denial on the protected namespace, without deleting anything. Use a disposable private cluster for cluster-wide or disruptive cases. A Slack invitation to staging is not a configured connection or a grant to execute a load test.

**Two independent verdicts.** On a PR, adapt the team's existing E2E suite and its Katana diff-to-test selector as described, rather than introducing another test suite. Validate its actual interface and privacy behavior before enrollment. Run selected deterministic cases and mandatory PR checks. If mapping is uncertain, widen the selection. Cache dependency maps, prepared environments and selection decisions keyed by repo, inputs, test catalog and policy. Do not use a prior pass as fresh evidence. Keep suggested test or code repairs on another branch, not in the run being graded.

For a nightly such as `v1.1.x.20261118`, record a manifest of included PR SHAs, merged SHA and deployed artifact digests. Deploy the actual bundle, run a fixed smoke each night (create a fixture resource, wait until usable, use it, delete it, check cleanup), then run changed workflows and risky interactions across PRs. Rotate broader scenarios and run the full relevant suite for high-risk changes, selector uncertainty or release policy. Live smoke and human release sign-off are separate from individual PR outcomes. Most healthy runs need no LLM calls. Use agents for genuinely unmapped behavior, ambiguous failures or explicitly budgeted exploration.

**Team-facing table of contents.** After *each* run update the machine-owned status/comment cells per workflow (leave human entries intact): feature, PR or bundle revision, pass/fail/blocked/not run, observed result, run ID and redacted evidence pointer. Example: `Resource creation | bundle <digest> | PASS | fixture became Ready, returned expected ID, then was removed | R42`. A closed browser window or a screenshot alone is not a backend assertion. Publish one idempotent update per run under an approved repo grant, preserve attempt history locally and queue publication offline without rerunning tests. Hold release sign-off when an applicable required row is blocked. No bulk posting raw logs, source or screenshots.

**Exploration feeds a Findings inbox, not the PR's failure count.** Take screenshots only inside a disposable browser/profile or dedicated native session, never the human's desktop. Use fixture accounts and record a bounded scenario, seed, action trace, target digest and expected versus actual behavior. Set limits on requests, rate, elapsed time, tokens and cleanup before starting. Disruptive stress runs belong on a disposable target, never shared staging by default. Store minimal redacted artifacts privately and expire them. If screenshots cannot be safely redacted, do not upload them.

Example: during a PR for resource creation, the agent notices a chart stops updating after reconnect. Create a suspected finding, deduplicate by symptom and scenario, and let an independent verifier replay the smallest reproduction against candidate and base. Candidate-only failure is a potential regression; failure on both is likely pre-existing; intermittent or conflicting results remain inconclusive. If needed, give a second worker a *different* hypothesis, not the first worker's conclusion. No vote can turn three guesses into a verified bug. Keep frequency, failures and clean attempts intact. The owner can confirm/file, dismiss with reason, or request more testing. A verified unrelated defect can block a release by severity without being falsely attributed to this PR. No automatic issue filing, code changes or external disclosure.

**First pilot:** one existing suite, one PR table row, one pinned nightly bundle, one staging smoke and one deliberately seeded unrelated UI finding. Show that the candidate and base can be distinguished, duplicate events don't duplicate comments or findings, an unauthorized target gets no data, and the environment cleans up even after cancellation. Only then add more runners or autonomous exploration.
## How a review gets its context

Think of four different questions: **Who may do what? What procedure should they follow? Where should they look? What actually happened?** Combining all four in a prompt makes it difficult to explain a decision and impossible to enforce a permission. This section distinguishes inspected source behavior from the proposed integration. It is not a packaged-client verification.

### What already exists

| Mechanism | What the source does | What not to assume |
|---|---|---|
| Instructions | The local HAL source (`src/agent/prompts.rs`, `src/config.rs`) reads configured files directly under the workspace. Defaults are `AGENTS.md`, then `HAL.md`, with a shared 32 KiB content cap. Philium adds shared instructions, editable `agent_rules`, eligible standing memories, a repo map when available, and the agent identity (`agents.rs`). | Not recursive subtree discovery. Do not assume `CLAUDE.md` or the user's current Jcode overlay is automatically honored. The installed HAL binary's behavior still needs a fixture check. Order in a prompt is not an authorization boundary. |
| Skills and playbooks | `library.rs` copies skills from configured local Jcode/Claude sources on initial import, with explicit re-import available. Skills are a desk-wide named library. `board.rs` resolves a job's `.philium/playbooks/<job>.md` before the user override and then the bundled default. | A skill describes how to do something. A playbook says which steps a job expects. Neither is permission to run a command, disclose code or approve a release. Imported skill bodies and attachments are data too. |
| Memory and history | Local SQLite stores active facts, preferences and corrections with scopes. Non-Strict agents can get global standing preferences/corrections in the initial prompt and request memories or session excerpts. Strict agents do not receive those standing memories or memory/history tools. Keyword memory lookup now filters global plus the requested project before ranking (`5d08a49`). | Memory is a curated claim, not a transcript or proof. Agent memory writes currently default to global unless project scope is requested, and a missing project can yield global. Session lookup can search across repos by default and uses path heuristics. Strict mode alone is not a per-repo disclosure policy: standing rules and a repo map can still enter prompts. |
| Code index and graph | `codeindex.rs` builds a local tree-sitter symbol/reference index of a default-branch snapshot with changed files overlaid per worktree. The Code screen requests `codeindex.graph`; agents can query the corresponding map, symbols, refs and impact without reading the entire repo. Separately, `graph.rs` offers Graphify or a capped file/import fallback. | The visual graph and agent-facing source index need not be two independent sources of truth. Name-based references are leads, not proof of runtime dependencies. An absent edge cannot rule out a config, generated-code, chart, service or cross-repo dependency. A stale/partial index must never mean “safe to skip.” |

### Proposed contract: one task, one explicit context boundary

1. **Choose the identity before reading.** Bind the task to a stable repo ID, exact revision (and dirty worktree fingerprint when applicable), purpose, permitted data classes, target, recipients and budget. Keep local browsing separate from model input, runner payload and published evidence. A grant for one is not a grant for the others. Missing identity blocks review recall and dispatch rather than widening the search.
2. **Resolve guidance deterministically.** Show a small local Context panel listing source/path, scope, revision or content hash, reason for inclusion and whether content was truncated. Defaults supply gaps; repo conventions and the selected playbook supply the procedure; the human supplies this task's intent. None can expand enforced permissions. For review, pin trusted workflow instructions from the base revision. If the PR changes instructions or required tests, show that change as review material rather than letting the candidate redefine its own pass criteria. Surface material conflicts for a decision.
3. **Retrieve the minimum useful context.** Give a worker one question. Query the current repo index for implicated symbols, immediate callers and matching tests. Fetch exact spans on demand. If the map is unavailable, explain that and fall back to bounded local search or broader tests. Fetch relevant *approved* repo memories, not a dump of history. Tag snippets with their source. A helper receives a narrower grant and its own packet, not the parent's transcript. For remote work, send an approved pinned artifact instead of source when it suffices.
4. **Record the run, not a new belief.** Store cases, actual observed results, blockers, environment, revision and redacted evidence in a run record. A finding links to the run and its candidate/base reproductions. Only an explicit promotion makes a finding or learned convention durable repo memory. Make memories inspectable, editable, revocable and attributable. When code changes, recompute graph data and retest affected cases. A correction supersedes a memory. An earlier observed pass remains true of the old revision only.

**Example:** An Exo PR changes resource creation. The team playbook requires create/use/delete. The graph points to a controller and its tests, but cannot establish that the deployed chart grants that controller the right permissions. Run the selected local tests, then the live smoke on the approved bundle and cluster. An agent spotting a frozen chart after reconnect creates a finding, not an Exo convention. Compare the same bounded scenario on base and candidate, keep screenshots private, and let the owner decide. Publishing the PR table should need only a status, observation and approved evidence reference. Neither Sentinel history nor the exploration transcript belongs in that update.

**Implementation order:** add an offline Context view to the local Review milestone. Build one shared resolver that applies the same identity checks to initial prompts, memory/history tools, skill attachments, graph targets and worker dispatch. Allow only explicit, narrow global items for reviews. Default new review memories to repo-private proposals and reject missing identity. Use harmless repo-A/repo-B markers, including same-basename repos, to test every surface with a local recording recipient. Verify zero outbound requests without a grant, exclusion of B from A's initial and subsequent packets, recognition of stale indexes, and no new permissions when candidate instructions request them. Only then enable one bounded executor and independent verification. Do not treat the single keyword-memory regression as proof of the wider boundary.
